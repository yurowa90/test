## 1. 약어의 지위 — 무엇이 어디서 왔는가

- **GRASPS는 ASCD 백서(McTighe & Wiggins 2012, *UbD Framework*)에 등장하지 않는다.**
  백서는 Stage 2의 진짜성·전이·여섯 측면만 다룬다.
- GRASPS 약어와 6요소 프롬프트의 1차 출처는 **W&M(2005) 제7장 "Thinking Like an
  Assessor", pp. 157–159**이며, Figure 7.7이 설계용 문장완성 프롬프트다.
- 따라서 앱의 인용 표기는 다음과 같이 분리한다.
  - Stage 1/정렬/여섯 측면 → 2012 백서 페이지 인용
  - GRASPS 6요소·프롬프트·예시 → W&M(2005) pp. 157–159, Fig. 7.7

## 2. 6요소 정의 (스키마 확정용)

| 키 | 원어 | 정의 |
|---|---|---|
| `goal` | Goal | 시나리오가 제시하는 목표·과제·해결해야 할 문제와 넘어야 할 장애 |
| `role` | Role | 학생이 맡는 역할(누구로서 수행하는가) |
| `audience` | Audience | 결과물을 받을 대상·의뢰인. 실재일 수도, 모사(simulated)일 수도 있다 |
| `situation` | Situation | 구체적 맥락과 그 맥락이 주는 제약·기회 |
| `performance_product` | Performance / Product | 기대되는 구체적 수행 또는 산출물, 그리고 그것을 만드는 목적 |
| `standards` | Standards | 사전에 학생에게 공개되는 평가 준거와 성취 기준 |

**⚠ 원문 내 표기 불일치(앱 설계에 영향):**
p.157 본문의 약어 풀이는 P를 *Performance*로 쓰지만, 같은 장의 예시 과제(세제 실험)는
같은 자리를 *Product*로 라벨링하고, Figure 7.7의 항목명은 *Product, Performance, and
Purpose*다. 2011 Guide는 "수행 또는 산출물"로 병기한다.
→ 내부 키는 `performance_product` 하나로 두고, UI 라벨만 "수행/산출물"로 병기할 것.
S를 두 번 세는(Standards/Situation) 혼동도 여기서 발생하므로 스키마에 주석을 남긴다.

## 3. Figure 7.7 프롬프트 — 생성기 입력 프레임

Figure 7.7은 각 요소마다 **빈칸을 채우는 문장 틀**을 제공한다. 아래는 그 기능을 한국어
설계 프롬프트로 옮긴 것(직역 아님). Pass 1에서 요소별 슬롯을 채울 때 이 틀을 쓴다.

- **Goal** — 과제는 ~하는 것이다 / 목표는 ~이다 / 문제(도전)는 ~이다 / 넘어야 할 장애는 ~이다
- **Role** — 당신은 ~이다 / 당신은 ~해 달라는 요청을 받았다 / 당신의 일은 ~이다
- **Audience** — 당신의 의뢰인은 ~이다 / 대상은 ~이다 / 당신이 설득해야 할 상대는 ~이다
- **Situation** — 당신이 놓인 맥락은 ~이다 / 이 도전은 ~을 다루는 일이다
- **Product/Performance/Purpose** — 당신은 ~을 위해 ~을 만들 것이다 / ~하도록 ~을 개발해야 한다
- **Standards** — 당신의 수행은 ~해야 한다 / 당신의 작업은 ~로 평가된다 / 산출물은 다음 기준을 충족해야 한다

네 항목(Goal·Standards)은 복수 문장 틀을 제공하므로, 생성기는 **한 요소에 대해 2~3개
후보 문장을 만들고 하나를 고르는** 구조가 원문 설계 방식에 더 가깝다.

## 4. 원문 예시의 구조적 특징 (few-shot 참조용)

W&M(2005) p.158의 과학 예시는 다변인 실험 설계 이해를 평가한다. 구조만 요약하면:

- Goal+Role을 **한 문장에 결합**했다(소비자 조사기관 연구원으로서 세제 성능 비교 실험을
  설계하라).
- Situation을 **2단 과제**로 쪼갰다: (1) 변인 통제 설계, (2) 타인이 재현할 수 있도록 절차를
  전달하기. → 전이(transfer)와 설명(explanation) 측면을 동시에 겨냥.
- Product는 형식을 지정하되(주어진 양식의 실험 절차서), 보조 표현(개요·도식)은 **선택**으로
  열어 둠 → UDL의 표현 수단 다양화와 충돌하지 않는 지점.
- Standards는 Product의 각 요구를 **1:1로 되받아** 진술됨. 루브릭 준거가 과제 진술에서
  기계적으로 도출된다.

→ 생성기 규칙: **Standards의 각 준거는 Product/Situation 진술의 어떤 구절에서
도출되었는지 역추적 가능해야 한다.** 대응되지 않는 준거는 삭제 대상.

다른 예시들(버지니아 4일 투어 기획, 회사 로고 형태의 화단 설계, 문학 명예의 전당 후보
추천서)도 동일 패턴이다: 실재하는 의뢰인 + 형식이 지정된 산출물 + 사전 공개 기준.

## 5. 사용 한계 — 과잉 적용 금지

- 원문은 **모든 수행평가를 GRASPS로 틀 지을 필요는 없다**고 명시한다. 다만 주요 단원이나
  과정에서 **이해를 평가하는 핵심 수행과제 최소 1개**는 이 방식으로 설계할 것을 제안한다
  (p.158).
- 시나리오가 억지스럽거나(contrived), 전통적 글쓰기 과제가 더 적합하다고 판단되면
  GRASPS를 강요하지 말라는 지침이 별도로 나온다(p. 174 인근).
- 2012 백서의 표현대로 수행과제는 **종합 수행(culminating performance)**이지 매 차시
  활동이 아니다.

→ 앱 동작: 사용자가 단일 차시 활동을 입력하면 "GRASPS 적합도 낮음" 경고를 띄우고,
단원 수준 종합과제로 승격할지 묻는다.

## 6. 여섯 측면과의 접속 (six_facets.md 연동)

2011 Guide Stage 2 카드는 수행과제가 여섯 측면(설명·해석·적용·관점·공감·자기이해)을
반영해야 한다고 본다. 단, 백서의 지침대로 **모든 측면을 다 넣지 말고 겨냥한 이해에
해당하는 측면만** 고른다.

Pass 2 루브릭 생성 시 준거 도출 경로:
```
겨냥한 이해(Stage 1) → 해당 여섯 측면 선택 → 측면별 관찰 가능한 행동 → Standards 준거
```

## 7. 정렬 점검 (quality_checklist.md와 중복 확인)

- 이 과제가 요구하는 것이 Stage 1의 **이해**인가, 아니면 단지 지식·기능인가?
- 학생이 **새롭고 진짜인 상황(new and authentic situation)** 에 적용하는가, 아니면
  배운 절차를 반복하는가?
- 준거가 **채점하기 쉬운 것**만 재고, 정작 중요한 이해가 틈으로 새고 있지 않은가?
- 이 과제를 훌륭히 수행하고도 목표한 이해가 없을 수 있는가? (있다면 과제가 잘못됨)
- 반대로, 이해했는데도 이 과제에서 실패할 수 있는가? (있다면 무관한 장벽이 있음 → UDL 점검)
